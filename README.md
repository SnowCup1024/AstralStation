# 星间驿站

私人 Windows 游戏工具箱，C# / WinUI，简体中文。当前版本 **Alpha 5.2**，暂不添加许可证。

Alpha 5.2 将运行日历移到独立侧边栏页面，启动管理只保留今日队列与任务库。日历同时展示启动队列和后台监测记录，并标明来源；原有历史保留，队列按各自每日重置时间归档，后台按观测开始的本地日期归档。两种来源分别保存，不将重复观测叠加为总时长。损坏记录单独提示，不隐藏其他可读取的记录。

Alpha 5.0 增加独立的用户会话后台进程 `AstralStation.Monitor.exe`。与 WinUI 主应用分离，关闭主应用仍可持续观测游戏；启用后独立登记 Windows 登录启动，应用更新时先保存并停止后台，重开后恢复。无需管理员权限，不作为 SYSTEM 服务运行。

后台每秒检查明确配置的进程，校验完整 EXE 路径、PID 和创建时间，拒绝同名程序误匹配；不同 Windows 会话隔离。权限不足时显示错误并保留运行状态，不误报游戏退出。每 10 秒保存观测检查点，意外中断后没有精确退出时间的记录按最后观测时间结束。只记录，不启动或终止游戏。Alpha 5.1 的后台清单默认空白，不自动导入启动任务。总设置的“实时进程监测”卡片位于启动管理与本地数据之间，提供手动添加、编辑、移除和推荐添加，只需要实际 EXE 路径与进程名称。推荐共用启动任务的安装检测逻辑，使用实际进程文件而非启动快捷方式；仍需选择确认，绝不自动加入。空 EXE 占位文件不能作为监测对象。终末地等不在原推荐清单内的游戏可手动添加。

## 构建与运行

需要 .NET SDK 10.0.402 与 Windows SDK 10.0.26100。运行 `./Build.ps1`，生成自包含应用目录及安装器、更新包：

`.build/Alpha-5.2/Installer/SnowCup1024.AstralStation-alpha-Setup.exe`

`Installer` 中的 Setup.exe 用于安装，`*-full.nupkg` 与 `releases.alpha.json` 用于更新；`App/AstralStation.exe` 供开发调试。默认按用户安装到 `%LOCALAPPDATA%/SnowCup1024.AstralStation`，数据目录保持不变，卸载保留用户数据。无需另装 .NET 或 Windows App SDK。安装器尚未签名。

发布更新时将当前 Installer 内的 Setup、full.nupkg、releases.alpha.json 上传至同一 GitHub 预发布 Release；源码推送不等于发布二进制更新。公共仓库更新源无需在客户端保存令牌，也支持选择本地更新目录离线更新。构建工具与 SDK 均锁定官方预览版 Velopack 1.3.39-g8d2844f，因为它包含 [Setup 传参崩溃修复](https://github.com/velopack/velopack/pull/1088)，1.2.x 会在传入应用参数时失败。



## 使用

- 今日队列：按任务顺序启动、等待、监测与记录；按今日完成状态显示“启动此任务”或“重试此任务”，未完成时显示“标注此任务为完成”，完成时显示“重置此任务进度”，全部重置位于右侧。
- 任务库：添加、编辑、排序、安装检测；所有任务均参加队列。支持程序、快捷方式与脚本。
- 运行日历：按各任务的每日重置时间归档。退出工具箱不会结束游戏。
- Steam 启动国服：按账号与路径、空EXE占位文件、ACF、Steam 启动选项四步配置终末地，前置步骤未完成时后续整张卡片置灰。支持 Steam 路径检测；进入游戏配置时自动补齐缺失的启动脚本，保留已有脚本。空 EXE 直接生成，显示已有文件的实际大小，已有文件时禁用生成按钮并提供悬浮说明；ACF 应用前显示具体变更，启动选项仅复制后手动填写。脚本保存在 `%LOCALAPPDATA%\AstralStation\SteamLaunch\4732690`。
- 设置：主题、安装与更新、启动管理（完成后行为、托盘、登录启动）、实时进程监测及本地数据统一放在总设置。自由调整窗口大小与最大化。最小窗口 800×600 逻辑像素；全界面跟随所在显示器 DPI，窗口变大不再放大控件。
- 同一数据目录只运行一个实例。新版接管旧版，同版或旧版再次打开时聚焦已有窗口。

自动检测仅覆盖指定游戏清单，跳过 Steam、模拟器和终末地；碧蓝航线暂未加入。安装信息或启动入口不足时可能漏检，可手动添加。默认本地 04:00 重置，可在任务库修改。

数据保存在 `%LOCALAPPDATA%\AstralStation\Launch`，包含任务、设置、完成状态和历史 JSON，以及 `.bak` 备份。`--paused` 暂停启动，`--data-dir "路径"` 指定独立数据目录，`--background` 在开启托盘时后台启动。Windows 登录启动会自动携带 `--login-startup` 来源标记。

开启 Windows 登录启动需要先安装，启动登记指向安装器维护的固定 `current/AstralStation.exe`；打开安装版时自动迁移原有的已开启登记，关闭的登记不会被开启。构建不修改启动项，开发目录运行不迁移启动项。更新会替换 current 内容，不再复制单个 EXE。卸载仅移除指向本安装目录的应用与监测启动项，保留数据。

游戏运行期间由工具自动最小化的窗口，会在游戏结束后自动恢复。启用倒计时退出时，最后一个游戏结束后同样先恢复窗口，再显示 15 秒退出倒计时。只有手动打开时发现今日任务已全部完成，才默认保持打开；Windows 登录自动启动时即使任务已完成也会倒计时。重置进度或再次运行任务后，完成时重新启用倒计时；弹窗中的“保持打开”仅对本次完成生效。还有运行任务、正在操作弹窗或记录保存失败时不会自动退出。

## 开发

维护与智能体规则见 [AGENTS.md](AGENTS.md)。每次构建后提交并推送；完成后清理旧版本、构建缓存和临时验证产物，仅保留开发文件及当前版本。禁止过度测试、哈希测试、冒烟测试和无意义循环验证。

后台数据位于数据目录的 `Monitor`：`config.json` 保存明确启用的清单，`active.json` 保存检查点，`History/日期/记录ID.json` 保存起止记录。后台和启动队列分开写入，避免多个进程覆盖同一个历史文件。命名管道仅允许当前用户连接，主应用可检查状态、请求保存退出；关闭主应用不会发出停止请求。

## Alpha 10.0 方案（尚未实现）

目标是让 Steam 仍能打开官方启动器，同时在其他入口启动终末地时，为这一段真实运行建立 Steam 计时会话。下面是基于现有脚本和后台能力的设计判断，Steam 是否实际累计时长仍须用当前客户端实测确认。

1. 将 Steam 直接启动的等待程序改为无控制台窗口的 WinExe 桥接程序，避免启动终端再隐藏。Steam 启动选项仍由用户复制填写，保留 `%command%` 但不执行空 EXE。原有自定义脚本保留，迁移展示变更预览。
2. Steam 启动桥接程序时，先与后台登记 AppID、会话标识和自身进程身份。如果实际游戏已运行，直接接管等待；否则打开官方启动器一次。后台可暂不可用，桥接程序应能自行等待游戏退出，不能让 Steam 一直显示运行。
3. 后台观测到明确加入清单的实际终末地进程时，先给正在启动的桥接程序一个短暂登记窗口；没有桥接会话才调用一次 `steam://rungameid/4732690`。等待桥接程序握手，超时显示失败并限制重试，禁止每秒重复调用。这个 URI 的返回进程不能当作游戏或终端的 PID。
4. 游戏退出后先经过数秒宽限，处理进程替换、短暂重启与多个同路径进程；确认全部退出后通知桥接程序正常结束。必要的兜底仅作用于本次登记的桥接程序，校验完整路径、PID、创建时间和会话标识，绝不能按 powershell.exe / conhost.exe 名称批量结束，也不能结束游戏或 Steam。
5. 只对用户明确开启联动的游戏生效。Steam 未启动或未能启动该 AppID 时，默认只保留本地记录并提示，不反复抢焦点。桥接程序可完全不创建窗口；Steam 客户端自身的登录、更新和确认界面不能承诺完全隐藏。计时桥接存活期间允许下载更新，延后应用更新，避免安装器替换正在被 Steam 计时的程序。
6. 先做一次真实 Steam 验证：分别从 Steam 与官方启动器进入游戏，核对客户端运行状态、退出后停止状态及累计时长；再验证进程重启、Steam 不在线和后台重启。若 Steam 不把桥接程序的生命周期认作该 AppID 的运行时间，则保留本地监测，不宣称已实现 Steam 时长同步。

Valve 文档确认通过 Steam 启动会建立应用的 Steam 上下文，且重启接口实质调用 `steam://run/<AppID>`；它没有承诺第三方等待进程的计时行为，不能用接口说明代替上述实测。[Steamworks API 概述](https://partner.steamgames.com/doc/sdk/api%20?l=english)。本方案不向终末地注入 Steamworks DLL，不伪造 `steam_appid.txt`。
